# ADR-0025: Cluster changes apply only the objects they touch

- Status: accepted
- Date: 2026-10-22
- Refines: FP7-F-14, hard rules 4 and 5, [ADR-0013](0013-k0s-control-plane-replacement.md) (rollouts)

## Context

Every cluster change (labels, scaling, upgrade, …) updates the stored spec, regenerates all
objects with `transform(spec)` and applied every object that differed from the live one
(FP7-F-14). The live objects, however, were generated by the app version that last applied them.
When a newer app version generates an object differently, the next change of any kind applied
that difference as well.

Seen live on 2026-10-22: a kubeadm all-in-one cluster created before a fix of the generated
`postKubeadmCommands` (LoadBalancer label, FP-26). Assigning an add-on changed only the cluster
labels, but the change also applied the new `KubeadmControlPlane` spec. CAPI rolled the only
control plane node. The rollout plan was in the preview, but nothing pointed out that it came
from the app version and not from the label change.

## Decision

- A change applies only the objects it touches: the backend generates the objects for the stored
  spec before and after the change with the **same, current** code (`objectsTouchedBy`, pure) and
  applies only those that differ between the two, plus objects that do not exist yet.
- Objects that differ from the live state only because of a newer app version are compared as
  unchanged, so they do not show up as rollouts, and the preview names them ("Not part of this
  change: … left as is, since applying it may replace machines").
- Namespace-wide objects the backend adds (namespace, cloud config Secret, add-on presets,
  ClusterResourceSets) keep their own rules; they do not replace machines.
- A change that replaces machines carries a warning at the top of the preview, and a stronger one
  when the only node of an all-in-one cluster is replaced.

## Consequences

- A label, scaling or bastion change never rolls machines because of an app update. A change that
  does touch an object (e.g. an upgrade touching the control plane) applies the whole object as the
  current code generates it, including the newer parts; the rollout happens anyway.
- Clusters can stay on objects of an older app version. Bringing them up to date is the explicit
  **reapply** change (FP7-F-19), which applies every generated object that differs from the live
  one, with its own preview, rollout plan and warnings; the preview of other changes points out the
  outdated objects.
- The comparison doubles the transformation per preview; it is pure and fast.
